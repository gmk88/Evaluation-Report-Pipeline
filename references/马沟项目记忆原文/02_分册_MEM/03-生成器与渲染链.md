## 生成器覆盖陷阱（判例 `PL-GEN-0008`）
- `build_review.py` **无参运行会覆盖根目录现行交付稿**，并重写构建清单/变更记录/目录缓存。
- 10-03 事故：为"只知道别人改了什么"就用 `build_review.py /tmp/x.docx` **试建对照稿**——当时 `__main__` 是 `main()` 无参调用，**参数被吞**，直接覆盖了用户 10:46 的交付稿。**动机是"只看看"不构成豁免，只要脚本会写现稿就先备份。**
- 已根治（10-03）：`__main__` 改为 `main(sys.argv[1] if len(sys.argv)>1 else None)`，传路径可安全试建；无参仍覆盖。
- **取证顺序**：要弄清别人改了什么 → 只读比对文本 → 再决定是否重跑生成器。**绝不用"跑一遍生成器"当取证手段。**
- 恢复来源：`~/.claude/file-history/<session-id>/<内容哈希>@vN`、`~/.claude/projects/<slug>/*.jsonl` 会话全文、以及**未被覆盖的交付 PDF**。
- **外部工具（Claude Code 等）直接改 DOCX 的成果，任何一次重建都会抹掉。** 第6章整章内容已固化进 `chapter6_data.py`，重建不再丢。
- **哈希只在同一次生成内稳定**（生成器写 zip 用当时时间戳、PDF 文档 ID 每次不同）：重跑或重渲染 → 哈希必变，**不能据此判断内容是否被改**；要比对逐页文本、字体集合、目录项数、页脚、非黑色 run。

## 落点定位陷阱：段落 id ∉ 章节（2026-10-04 第六批实案）
- `mago_paragraphs.json` / `exposure_proposals.json` 的 **id 只是原稿段落序号，与章节无对应关系**。
  同一条 `paragraph_replacements` 可能落在**任意一章**：1260／1261 看着像「4.3 正文」（前一条是 875＝4.3.3），
  实际是 **11.1 评价结论**的第 4、5 条；本轮据此误改后已回退。
- **改前必做的两步**：① 用 `mago_paragraphs.json` 查该 id 的原文，确认它属于哪一节（找最近的标题段）；
  ② 拿 PDF **反查物理页**——`''.join(p.extract_text().split())` 后搜原句片段，看它出现在哪一页、该页页眉栏属于哪章。
  两步都过了再动手。**"这个 id 看着像在哪一节"不构成依据。**
- 排查命令范式（本项目环境，pypdf 只在托管 venv 里有）：
  `for i,pg in enumerate(r.pages): t=''.join(pg.extract_text().split()); print(i+1, '关键词' in t)`。
- **回退手段**：每轮动手前已备份 `exposure_*.json`，用 id 对 id 逐字回退即可（本轮这样干净回退了 1260／1261）。

## 分节符被删陷阱（2026-10-03 新增，判例 `PL-GEN-0024`）
- `sectPr` 挂在某段落的 `pPr` 里，**删段落＝删分节符**。本轮 `remove(698)` 删第3章 3.4 的旧第4条，
  连带删掉「正文纵向→表4.3-1 起横向」的分界，横向节从正文第1页吞到下一个分节符：
  **75 页 → 87 页，正文第 1—36 页全变横排**。
- **症状具误导性**：页数在改动点**之前**就膨胀（第2章 19→21、第1章 +2），而内容一处没多加。
  差一点误判成「新增三张表把排版撑爆」，去调列宽字号——方向全错。
- **排查顺序**：先打整本横纵序列 `''.join('L' if p.rect.width>p.rect.height else 'P' for p in doc)`
  与基线逐位比对（错位＝节属性问题）；序列一致而页数仍差，才去查内容。
- **改法**：承载 `sectPr` 的段落**只能 `replace()` 改文字，不能 `remove()`**。
- **已加硬闸门**（序列化前，`build_review.py` 末段）：原稿携带 `sectPr` 的段落若 `getparent() is None`
  即抛错；再断言分节符总数 ≥14。第6章整章替换区间（`ch6_head`—`ch7_head`）显式豁免，属有意废弃。
- 对照实验方法（本轮用过，可复用）：复制生成器为 `_ab.py`，在待验证代码块**前一行**插
  `after=lambda *a,**k:None` 关掉某类动作，其余不动——比正则删代码块可靠（正则会把相邻的
  `replace()` 一起吃掉，得出假结论）。注意 Python 会把该名字当局部变量，故只能整段关、不能只关一部分。
- 每次对照实验后**删掉临时脚本**（`_ab_ch3.py`／`_diag_ch3.py`），别留在现役目录里。

## 运行环境与渲染定稿流程
- 跑本项目脚本**必须用 `/Users/a1234/homebrew/bin/python3`**（终端 `python3` 解析到托管解释器 3.13.12，**无 PyMuPDF／lxml**）。
- `render_review.py` 依赖固定路径 `/Users/a1234/.cache/codex-runtimes/codex-primary-runtime/dependencies/bin/override/soffice`；渲染必须显式加载 `_work/fontconfig_qa.conf`（仿宋→FangS-SC、宋体→SimSun）；出现 FrankRuhlHofshi／LinuxLibertine 即不可交付。macOS 无 `timeout`。
- **定稿至少渲染 2 次**：`render → finalize 回填 → render → finalize --check`。目录页码与页脚「第X页共YY页」是**静态文本**，只能按实际渲染的 PDF 回填。`finalize_review.py --check` 不渲染，要先自己渲染再喂 PDF。
- 复现命令：`build_review.py`（无参覆盖根目录稿）→ `render_review.py ../out/final` → `finalize_review.py <pdf>` → 再渲染 → `finalize_review.py <pdf> --check`。
- **只改 DOCX 必须同步改生成器**，否则下次重建退回旧内容。全量渲染约 5 秒，不是瓶颈；瓶颈是重建生成器与逐页目视检查。

## 渲染器视角必须与用户对齐（用户当场纠正过）
- 我用 LibreOffice headless 转 PDF ＋ PyMuPDF 逐页读；**用户用 WPS 看 DOCX**。两者对同一份 docx 的分页结论可以不同，所以「跨页/不跨页」结论**必须写明是哪个渲染器看的**。
- 本机**无法程序化驱动 WPS**（无 CLI、无 `*.sdef`、无 QuickLook 插件）；Word 的 AppleScript 导出报 -10004 权限违例；`wps-knowledgebase` 技能只是金山知识库云端 CLI，**不能渲染本地 docx**。
- 可行对齐办法：请用户在 WPS 里「输出为 PDF」交来当基线，或截图；同时我把自己渲染的页面图给对方看。
- **浮动表（`tblpPr`）是分歧高发区**：LibreOffice 按文本区下边界（横向页 y≈505）判→溢出行另起页并重复表头；WPS 按页面下边界（y≈595）判→整表留一页。表4.1-1 就是这种。
- 教训：**用户说"我看是好的"时，先怀疑自己的渲染器**，不要只用一种渲染器的结论宣布"无解"。

## 脚本里定位某张表的正确姿势（2026-10-04 踩坑）
- **不要用整表文本 `contains` 找表**：`'工种（岗位）' in ''.join(tb.itertext())` 会**先命中第 3 章的表3.2-1**
  （它有一行「c 接触情况｜各工种（岗位）危害因素识别、接触人数…」），把边框补丁打错表，
  实测把表3.2-1 第 4 列整列刷成黑色横线（36／37 页出现 5 条粗细混排线）。
- **正确做法**：取 `tbl.findall(W+'tr')[0]`（表头行）的文字，要求**同时命中两个特征词**（如「工种（岗位）」＋「接触时间和频度」），
  并在代码里留注释说明为什么不能用整表文本。
- **改完必须全篇复扫**，不能只看目标表：本次是靠「按 y 分组找粗细混排行」的全篇扫描才发现误伤，又靠它确认修复只落在目标表。
