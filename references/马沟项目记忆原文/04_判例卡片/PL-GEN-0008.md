# 不得用旧生成器覆盖当前报告

## 触发场景

工作区里可能同时躺着好几代生成器。它们看起来都能跑，但旧的那几个知道的是旧结构、旧口径，跑出来就覆盖现稿。

## 做法

**错误做法**：调用早期全量生成器（`_work/build_report.py`、`chapters.py`）覆盖当前报告；或直接无参数运行 `build_review.py`——它会覆盖根目录现稿，还会重写构建清单、变更记录和目录缓存。更隐蔽的一种：把「输出到临时路径试跑」当成安全动作——`build_review.py` 忽略 `sys.argv`、`main()` 无参调用，`python build_review.py /tmp/x.docx` 照样覆盖根目录现稿。

**正确做法**：先备份并比较现稿与原快照，确认无用户手改后再局部执行。注意 `build_review.py` 的测试输出即使传 `output=...` 也会改写工作底稿 JSON，不能视为无副作用操作。想验证脚本能否复现现稿，必须先把现稿和交付 PDF 复制到独立目录，再运行脚本，并用内容比对（逐页文本、字体集合、目录项数）确认前后一致。

## 依据

- 项目：交接文件 §十一「不要调用早期 `_work/build_report.py`、`chapters.py` 或旧预评价全量生成器覆盖当前报告。`build_review.py` 无参数运行会直接覆盖根目录现稿……执行前必须保存备份」（F3）
- 脚本：现行生成器为 `_work/pre_eval_red_review_20260930/build_review.py`
- 实测（2026-10-02）：`python3 build_review.py /tmp/repro_check.docx` 覆盖了根目录交付稿，交付稿哈希 `54b220dc…` 被替换为 `0c2428ac…`（F3）

## 可复用规则

> 任何会写根目录现稿的脚本，执行前必须先备份；脚本忽略命令行参数时，「指定输出路径」不是安全动作，脚本照旧覆盖现稿。

## 反例或例外

若脚本明确用 `argparse` 接收输出路径并只在 `__main__` 里按参数调用，则传路径是安全的——但必须以源码确认，不能凭命令行形式推断。

## 事故恢复要点（2026-10-02）

交付稿被覆盖后能恢复的依据不是备份的 DOCX，而是**未被覆盖的交付 PDF**：重新渲染新 DOCX，与交付 PDF 逐页比对文本，确认除目录页码占位外 60/60 页一致，再用 `finalize_review.py` 从渲染 PDF 回填目录页码、`--check` 通过，即内容零损失。所以**交付 PDF 必须与 DOCX 同时留存**，它是最后一道还原依据。

## 重犯与根治（2026-10-03）

同一个坑在 2026-10-02 记了卡之后**第二天又踩了一次**：为弄清「用户用别的工具改了什么」，以「试建一份对照稿」的名义跑了生成器，参数被吞，覆盖了用户当天 10:46 的现行交付稿。教训：**知道这个坑不等于不会踩；只要动手的动机是「只想看看」，就必须先备份。**

根治动作（2026-10-03 已落地）：

```python
if __name__=='__main__':
    import sys
    main(sys.argv[1] if len(sys.argv)>1 else None)
```

修复后已实测：`build_review.py /tmp/probe_check.docx` 生成到 /tmp，根目录现稿哈希不变。

**另一条更有价值的恢复来源 —— Claude Code 的文件历史。** 若被覆盖的稿是 Claude Code 编辑过的，可从 `~/.claude/file-history/<session-id>/` 找回：目录内按内容哈希命名、带 `@v1…@vN` 版本号，可用 `file` 与首行内容识别（生成器脚本会显示为 `Python script text`）。2026-10-03 即据此确认了 Claude Code 当时的 `build_review.py` 与磁盘版本一致。同时 `~/.claude/projects/<slug>/*.jsonl` 存整段会话记录，可用于还原操作序列。
