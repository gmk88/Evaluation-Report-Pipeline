# 哈希只在同一次生成内稳定，不能用来判断内容是否被改

> 一条判例只讲一件事。写不成一句话的，拆成两条。

## 触发场景

长周期报告工作区习惯「只认哈希」。但一旦你重跑生成器或重新渲染，哈希必然变化——这时若把哈希当成内容指纹，就会误判。

## 做法

**错误做法**：发现哈希对不上就断定文件被覆盖、内容被改，进而回退或重做；或者反过来，看到哈希没变就断定内容没动、跳过复核。

**正确做法**：先明确哈希的稳定性边界。DOCX 的哈希受 zip 条目时间戳影响（写包时取当前时间），PDF 的哈希受每次渲染生成的文档 ID 影响。因此**同一份产物在同一次生成内哈希稳定，跨生成必然不同**，「重跑 → 哈希变」属正常现象。

判断内容是否被改，改用内容比对：逐页文本（规范化空白后按页比对）、PDF 字体集合、目录项数、正文页脚「第 X 页共 Y 页」、DOCX 非黑色文字 run 数、包内媒体文件哈希。全部一致即认定未改动，并把新哈希登记为新基线；任何一项不一致才去定位差异。

同时记住哈希不能证明内容正确：内容改了但没重新生成，哈希一样相同。

## 依据

- F3 实测：重跑 `build_review.py`，DOCX `54b220dc…` → `0c2428ac…`；渲染后与交付 PDF 逐页比对 **60/60 页文本完全一致**，唯一差异是目录 4 页的页码仍是占位 `0`。
- F3 实测：用 `finalize_review.py` 回填页码后再渲染，与新稿再比对仍 60/60 页一致，字体集合（FangS-SC／SimSun／TimesNewRomanPSMT）一致，`--check` 通过。
- F3 实测：`render_review.py` 每次渲染产出的 PDF 哈希都不同，即使 DOCX 未变。

## 可复用规则

> 哈希只在同一次生成内稳定（zip 时间戳、PDF 文档 ID 每次都变），跨生成必然不同；判断内容是否被改要逐页比对文本与字体集合，不能只用哈希。

## 反例或例外

反过来也成立且更危险：哈希相同并不保证内容正确——内容改了但恰好没触发重新生成时，哈希同样相同。哈希只能证明「同一个文件」，不能证明「文件是对的」。
